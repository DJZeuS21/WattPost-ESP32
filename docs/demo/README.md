# Documentation screenshots

These fixtures exist only to document the local WattPost interface. They do not
simulate the full firmware, connect to hardware, or provide a public demo service.

## Source and capture

- UI: unchanged files from `esp32_monitor/web/`, served directly from this checkout.
- Version: read from `esp32_monitor/VERSION`; the HTML version placeholder and
  `/js/transport.js` alias resolve as they do in the existing development host.
- Capture: Chromium through Playwright, Ukrainian locale, `Europe/Kyiv` time zone,
  desktop width 1600 CSS pixels and mobile width 390, device scale factor 1.
- Wall clock: 24 October 2026, 20:00 Kyiv (17:00 UTC). Only the browser wall clock
  is fixed; application timers, polling, navigation and rendering run normally.
- The script clicks the real tabs, period buttons, metric selectors and settings
  search. Data enters through the regular local API. It waits for history loading
  to finish and for fonts before capturing. No styles, DOM text, charts or
  application state are patched.
- Desktop History and BMS Settings include the full page. Dashboard overview and
  mobile previews end at existing card boundaries. `dashboard-full.png` includes
  the full desktop panel. There is no image compositing or retouching.
- `first-setup.png` is the earlier documentation capture and is not regenerated by
  this fixture. It has no battery telemetry.

The recorded browser version, source commit, web tree identifier, chart point
counts and checks are in [capture-report.json](capture-report.json). The source
commit predates the documentation commit; the web tree identifies the unchanged
UI independently of later documentation edits.

## Synthetic battery model

`telemetry.py` generates 2017 records spanning 14 days, including both endpoints,
with a fixed random seed (`24102026`). It integrates current every minute, then
averages ten-minute buckets, matching the firmware history cadence. The initial
bucket includes the preceding nine minutes. This is a simplified illustrative
model, not a battery performance prediction or a configuration guide.

| Quantity | Relationship |
| --- | --- |
| Net power | Simulated solar production minus household demand |
| Demand | Base load, compressor cycles, morning/evening appliance peaks and small variations |
| Solar production | Daylight envelope, daily weather factors and sustained cloud dips |
| Charge control | Reduced surplus near 98.5% charge; reduced draw near the reserve floor |
| Current and voltage | Solve `P = I × (Voc + I × R)` with positive current for charging and `R = 0.012 Ω` |
| State of charge | Integrate current against 280 Ah, with 99.5% charge efficiency |
| Cells | Pack voltage divided among 16 cells with fixed deviations and small sensor noise |
| Temperatures | First-order thermal response to ambient temperature and current squared; battery response is slower than MOSFET response |

The stored SOC is rounded to whole percent, current to 0.1 A, cell voltages to
1 mV and temperatures to 0.1 °C. Pack voltage is the sum of rounded cell voltages.
Power and energy are calculated by WattPost from those values; they are not
injected as independent chart series. The live snapshot uses the final history
record, including its averaged readings. The settings fixture specifies all 53
parameters explicitly, with a `DEMO` device name and invented serial number.

`validate()` checks timestamps, cadence, topology, voltage sums, SOC bounds and
changes, plausible cell voltages and battery temperatures, charge/discharge
coverage and agreement between live and historical readings. Browser checks
cover 24-hour, seven-day and 14-day loading, settings search, populated rows,
chart data, console errors and horizontal overflow.

## Reproduce locally

Prerequisites: Python 3.10+, Node.js and Playwright with Chromium installed. No
ESP32, BMS, account, internet API or firmware build is needed. These developer
commands are separate from the [user installation guide](../INSTALLATION.en.md).

1. Start the documentation host from the repository root:

   ```sh
   python3 docs/demo/serve.py
   ```

2. In a second terminal, run the capture script. If Playwright is installed
   globally, make it available to Node with `NODE_PATH`:

   ```sh
   NODE_PATH="$(npm root -g)" node docs/demo/capture.cjs
   ```

   Set `WATTPOST_SCREENSHOT_DIR` to an absolute temporary directory to review
   images before replacing the committed ones. The generated report is written
   to that output directory; copy the reviewed report to `docs/demo/` alongside
   the reviewed images in `docs/screenshots/`.

3. Inspect all PNGs at their original size and at README display width. Review
   `capture-report.json`; an error or missing required data makes capture fail.
   Run `python3 docs/demo/telemetry.py` to check the model without a browser.

The host binds only to `127.0.0.1:8765`. It supports only GET, never proxies API
requests, and returns 404 for API routes without fixtures. The capture browser
blocks requests to other origins and all non-GET requests. It therefore cannot
read a real BMS or change a device setting. Stop the host after capturing.

Keep this document, the generator and captions in both gallery languages aligned
when changing the scenario, capture dimensions, validation or source UI. Do not
edit firmware or production UI to improve documentation screenshots.
