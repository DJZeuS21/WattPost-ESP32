# WattPost Web UI localization (UA / EN)

The canonical source lives in `esp32_monitor/web`; the exact same JavaScript
assets are packed for ESP32 and Cloud Device UI. Cloud-only pages use them via
`/device-assets/js/`. ESP32 has no external network dependency for translation.

## Translation architecture

- `js/i18n.js`: language preference, `t(key)` and explicit DOM bindings only.
- `js/i18n-uk.js`: Ukrainian translations, keyed by stable IDs.
- `js/i18n-en.js`: English translations, with the same IDs as UA.
- Static **text-only** HTML: `<span data-i18n="nav.dashboard">Панель</span>`.
  Keep Ukrainian fallback text for browsers with scripts disabled.
- Dynamic UI: `WattPostI18n.t('battery.voltage')` rather than Ukrainian/English
  inline strings. Do not use the displayed source phrase as an identifier.
- Dynamic values: `WattPostI18n.t('setup.found_count', { count: 5 })` resolves
  placeholders such as `{count}` **after** choosing the language. Placeholder
  values are inserted literally and must be rendered with `textContent`/safe
  DOM APIs, not interpolated into `innerHTML`. A user-provided SSID or BMS name
  must never be treated as a translation key.
- Values from APIs, user-defined device names, SSIDs, and identifiers are NOT
  translation keys. Use `textContent` for direct insertion or HTML escaping
  in a necessary markup template; `data-i18n-ignore` remains a clear
  marker for untrusted values but no observer scans text anymore.

When adding or changing copy, update both locale dictionaries (do not change
an existing key because the words changed), then run `web/tests/test-i18n.mjs`
and related browser tests. Missing keys must not be silently introduced.

## Choice and browser origin

Explicit `UA / EN` choice is persisted as `wattpost.language` in localStorage.
The first visit uses browser `en-*` => English; otherwise Ukrainian. First Setup
runs on `192.168.4.1` (another localStorage origin), so its success links carry
`?lang=uk|en` to transfer a manually chosen language to `bms.local`/LAN IP.
The Cloud pages and Cloud Device UI share one origin and preference.

## Migration debt and adding languages

Existing dynamic sections were written before localization. First Setup,
Dashboard, History, Device Settings and shared Cloud device status/navigation
now use direct keys in `js/setup.js`, `dashboard.js`, `history.js`,
`device-settings.js` and `app.js`. First Setup has 34 static bindings in
`setup.html`; Device Settings has 82 in its dynamic layout. History uses
`Intl.PluralRules` for record counts. Cloud device names, BMS models/names,
Wi-Fi SSIDs, signed-release changelog content and sensor labels are not
translation keys, and must bypass legacy source lookup.
JK BMS Settings now uses catalog keys for all 53 parameter names,
section descriptions and temperature subgroups, with immutable API IDs kept in
`SETTINGS_SCHEMA`. The UA view preserves an English reference under each
technical label; the EN view presents English without duplication. The shared
runtime's `tLocale(locale, key)` provides optional reference translations
without embedding language strings in schema source. Search covers both locales
and the API key in either view. The normalizer translates booleans, uptime, and
localizable units independently of the BMS data.
All seven Cloud-only pages and `cloud/frontend/app.js` now use direct keys
for static and dynamic text. The runtime supports `data-i18n-aria-label` and
`data-i18n-title` for static accessible names; Cloud page document titles are
set by `app.js`. Never wrap text inside `<title>` with an HTML element.
Cloud error-code IDs, resend countdown, account/pairing confirmation, last-seen
and rename strings use keyed templates. Interpolated values remain unmodified.
Shared local `index.html` and `setup.html` now explicitly bind static text
and titles/ARIA attributes as well. The live BMS status badge intentionally
retains its trailing text node because `app.js` updates `lastChild.nodeValue`;
do not wrap that node without adapting the status renderer and its tests.
The BMS badge's initial text is set via `app.js` with a keyed string.
`api.js` and `data-normalizer.js` carry semantic offline/online
`messageKey` values, not translated source text. The pure data normalizer
exports locale-independent `SENSOR_NAME_MAP` / `SENSOR_NAME_KEY_MAP`,
and Dashboard/History translate known sensor names at render time.
Unknown names remain literal and are escaped at HTML sinks; do not call
`t(name)` on device-provided data. Flow colors keep language-neutral
state IDs while their optional labels use catalog keys.

There is no source-phrase lookup, EN regex compatibility, global text
walker or mutation observer. After dynamically injecting markup containing
`data-i18n` attributes, explicitly call `WattPostI18n.apply(container)`.
DEV_ONLY assets do not participate in production localization.

Adding a language later requires a new `js/i18n-<code>.js` catalog with matching
keys, its inclusion in the ESP32 and Cloud packagers and allowlists, extending
the supported language and selector options, and browser/packaging regression.
No NVS, BLE or firmware protocol changes are required.
